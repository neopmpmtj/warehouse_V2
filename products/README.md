# CentCompras MVP

> **Current status lives in the root [`README.md` → Project status](../README.md#project-status-handoff).** This file is a **historical build log** of how the catalogue and offline layer were first assembled. Do not treat the early sections (CLI-only insert, three-field `Product`, admin-only management) as the live app.
>
> **Live facts (August 2026):** warehouse staff manage products at `/manage/products/`; new products start inactive (Genesis); families and suppliers have console drawers and PostgreSQL audit logs; `GET /api/products/` returns active rows plus `catalog_updated_at`; Service Worker cache is `centcompras-shell-v5`. **Stock is still typed on the product.** Inbound receipts from suppliers are the next product-side design; branch orders wait. The branch page at `/` remains a scaffold until a dedicated UX session.

A small **offline-capable warehouse product catalogue web app** built with:

- Python
- Django
- PostgreSQL
- Plain HTML
- Plain JavaScript
- IndexedDB
- Service Worker / Cache API

The purpose of this MVP is to build the system **from the foundation upward**, keeping each responsibility in a separate reusable module so that the developer can understand the whole flow instead of receiving a large finished application all at once.

---

## 1. Business scenario

A company has a central warehouse.

Users access a web app from a phone browser to see products and, later, place orders.

The important constraint is that users may travel through geographical areas with **little or no mobile data coverage**.

Therefore, the app must eventually work like this:

```text
ONLINE
Phone browser
    ↓
Web app
    ↓
Django API
    ↓
PostgreSQL


OFFLINE
Phone browser
    ↓
Cached web app
    ↓
IndexedDB
    ↓
Last known product catalogue remains visible
```

Later, orders created while offline will also be stored locally and synchronized when connectivity returns.

That order functionality is **not implemented yet**.

# 2. Important design decisions

## Server database is the source of truth

PostgreSQL is the master database.

Current database name:

```text
centcompras_db
```

The browser's IndexedDB is only a **local cache**.

It is not an independent warehouse database.

---

## Products cannot be created from the phone

For this MVP, products are inserted only through a Django CLI command.

Example:

```bash
python manage.py add_product "Cement 50kg" 100 12.95
```

There is intentionally **no web or phone feature for creating products**.

The phone/browser only downloads and caches the catalogue.

---

## Product fields

The MVP product contains:

```text
id
description
stock
price
```

`id` is automatically generated by Django.

`stock` supports fractional quantities.

`price` is stored with decimal precision rather than floating-point arithmetic.

Currency for the MVP is USD.

# 8. Reusable product service

File:

```text
products/services.py
```

Contents:

```python
from decimal import Decimal

from .models import Product


def create_product(description, stock, price):
    product = Product.objects.create(
        description=description,
        stock=Decimal(str(stock)),
        price=Decimal(str(price)),
    )

    return product


def get_products():
    return Product.objects.all().order_by("id")
```

## Why this file exists

The application keeps reusable business/database operations in one place.

Instead of writing:

```python
Product.objects.create(...)
```

in every CLI command, API view, or page, other parts of the application call:

```python
create_product(...)
```

Similarly, catalogue reads go through:

```python
get_products()
```

This is the beginning of a reusable service layer.

```python
from django.core.management.base import BaseCommand

from products.services import create_product


class Command(BaseCommand):
    help = "Add a new product"

    def add_arguments(self, parser):
        parser.add_argument("description", type=str)
        parser.add_argument("stock", type=str)
        parser.add_argument("price", type=str)

    def handle(self, *args, **options):
        product = create_product(
            description=options["description"],
            stock=options["stock"],
            price=options["price"],
        )

        self.stdout.write(
            self.style.SUCCESS(
                f"Product created: ID={product.id}, {product.description}"
            )
        )
```

# 15. IndexedDB

File:

```text
products/static/products/js/db.js
```

Contents:

```javascript
const DB_NAME = "centcompras";
const DB_VERSION = 1;

const PRODUCT_STORE = "products";
const META_STORE = "sync_metadata";


function openDatabase() {
    return new Promise((resolve, reject) => {
        const request = indexedDB.open(DB_NAME, DB_VERSION);

        request.onupgradeneeded = function (event) {
            const db = event.target.result;

            if (!db.objectStoreNames.contains(PRODUCT_STORE)) {
                db.createObjectStore(PRODUCT_STORE, {
                    keyPath: "id"
                });
            }

            if (!db.objectStoreNames.contains(META_STORE)) {
                db.createObjectStore(META_STORE, {
                    keyPath: "key"
                });
            }
        };

        request.onsuccess = function () {
            resolve(request.result);
        };

        request.onerror = function () {
            reject(request.error);
        };
    });
}


async function saveProducts(products) {
    const db = await openDatabase();

    return new Promise((resolve, reject) => {
        const transaction = db.transaction(
            [PRODUCT_STORE, META_STORE],
            "readwrite"
        );

        const productStore = transaction.objectStore(PRODUCT_STORE);
        const metaStore = transaction.objectStore(META_STORE);

        productStore.clear();

        for (const product of products) {
            productStore.put(product);
        }

        metaStore.put({
            key: "last_updated",
            value: new Date().toISOString()
        });

        transaction.oncomplete = function () {
            resolve();
        };

        transaction.onerror = function () {
            reject(transaction.error);
        };
    });
}


async function getCachedProducts() {
    const db = await openDatabase();

    return new Promise((resolve, reject) => {
        const transaction = db.transaction(
            PRODUCT_STORE,
            "readonly"
        );

        const store = transaction.objectStore(PRODUCT_STORE);

        const request = store.getAll();

        request.onsuccess = function () {
            resolve(request.result);
        };

        request.onerror = function () {
            reject(request.error);
        };
    });
}
```

## What IndexedDB does here

It stores:

```text
products
sync_metadata
```

Example conceptual structure:

```text
centcompras
│
├── products
│   ├── id
│   ├── description
│   ├── stock
│   └── price
│
└── sync_metadata
    └── last_updated
```

This does **not** let the user create warehouse products.

`saveProducts()` means:

> Save the catalogue received from the server into the browser's local cache.

It does **not** mean:

> Create a new warehouse product from the phone.

That distinction is important.

# 16. Frontend product loading

File:

```text
products/static/products/js/product_list.js
```

Current contents:

```javascript
async function getProducts() {
    const response = await fetch("/api/products/");

    if (!response.ok) {
        throw new Error("Server unavailable");
    }

    const data = await response.json();

    return data.products;
}


function displayProducts(products) {
    const tableBody = document.getElementById("product-table-body");

    tableBody.replaceChildren();

    for (const product of products) {
        const row = document.createElement("tr");

        const idCell = document.createElement("td");
        idCell.textContent = product.id;

        const descriptionCell = document.createElement("td");
        descriptionCell.textContent = product.description;

        const stockCell = document.createElement("td");
        stockCell.textContent = product.stock;

        const priceCell = document.createElement("td");
        priceCell.textContent = product.price;

        row.append(
            idCell,
            descriptionCell,
            stockCell,
            priceCell
        );

        tableBody.appendChild(row);
    }
}


async function loadProducts() {
    try {
        const products = await getProducts();

        await saveProducts(products);

        displayProducts(products);

    } catch (error) {
        const cachedProducts = await getCachedProducts();

        displayProducts(cachedProducts);
    }
}


loadProducts();


window.addEventListener("online", () => {
    console.log("Connection restored. Refreshing products...");
    loadProducts();
});


setInterval(() => {
    if (navigator.onLine) {
        loadProducts();
    }
}, 30000);
```

# 17. How the online/offline product flow works

## When online

```text
Page starts
    ↓
loadProducts()
    ↓
getProducts()
    ↓
GET /api/products/
    ↓
PostgreSQL catalogue returned
    ↓
saveProducts()
    ↓
IndexedDB updated
    ↓
displayProducts()
```

## When API/server/internet is unavailable

```text
loadProducts()
    ↓
getProducts()
    ↓
request fails
    ↓
catch
    ↓
getCachedProducts()
    ↓
IndexedDB
    ↓
displayProducts()
```

The user therefore sees the **last successfully downloaded catalogue**.

The displayed stock should eventually be labelled as last-known stock, because stock could have changed at the warehouse while the phone was offline.

# 18. Service Worker

File:

```text
products/templates/products/service_worker.js
```

Current version:

```javascript
{% load static %}

const CACHE_NAME = "centcompras-shell-v3";

const APP_SHELL = [
    "/",
    "{% static 'products/js/db.js' %}",
    "{% static 'products/js/product_list.js' %}",
    "{% static 'products/js/register_sw.js' %}"
];


self.addEventListener("install", (event) => {
    event.waitUntil(
        caches.open(CACHE_NAME)
            .then((cache) => cache.addAll(APP_SHELL))
    );

    self.skipWaiting();
});


self.addEventListener("activate", (event) => {
    event.waitUntil(
        caches.keys().then((cacheNames) => {
            return Promise.all(
                cacheNames
                    .filter((name) => name !== CACHE_NAME)
                    .map((name) => caches.delete(name))
            );
        })
    );

    self.clients.claim();
});


self.addEventListener("fetch", (event) => {

    // Do not cache API calls here.
    // If the API fails, product_list.js falls back to IndexedDB.
    if (event.request.url.includes("/api/")) {
        return;
    }

    event.respondWith(
        caches.match(event.request)
            .then((cachedResponse) => {
                return cachedResponse || fetch(event.request);
            })
    );
});
```

The Service Worker caches the **application shell**:

```text
/
db.js
product_list.js
register_sw.js
```

IndexedDB separately stores the **product data**.

Think of the difference as:

```text
Service Worker Cache
    → keeps the app itself available

IndexedDB
    → keeps the catalogue data available
```

# 20. Important bug encountered and fixed

Initially, `register_sw.js` was not included in the Service Worker's `APP_SHELL`.

When Django was stopped, Firefox produced an error similar to:

```text
Failed to load:
http://localhost:8000/static/products/js/register_sw.js
```

The page still displayed products because the other required files were already cached, but `register_sw.js` itself was missing.

The fix was to add:

```javascript
"{% static 'products/js/register_sw.js' %}"
```

to:

```javascript
APP_SHELL
```

and change the cache version, for example:

```javascript
centcompras-shell-v2
```

to:

```javascript
centcompras-shell-v3
```

Changing the cache version is important when cached application files are changed.

# 21. Automatic retry when connectivity returns

Originally, the app would reload fresh data only when the page was manually refreshed.

This was improved.

The browser now listens for:

```javascript
window.addEventListener("online", ...)
```

When the browser reports that networking is available again, it calls:

```javascript
loadProducts();
```

The app also retries every 30 seconds while it is open:

```javascript
setInterval(() => {
    if (navigator.onLine) {
        loadProducts();
    }
}, 30000);
```

This means the expected behaviour is:

```text
No internet
    ↓
User sees cached catalogue
    ↓
Network returns
    ↓
Browser fires "online"
    ↓
App tries /api/products/
    ↓
Fresh catalogue downloaded
    ↓
IndexedDB updated
    ↓
Displayed catalogue updated
```

The periodic retry acts as a backup.

`navigator.onLine` should not be treated as proof that the Django server itself is reachable; therefore the actual API request remains the final test.

# 25. Planned next major phase

The next major feature is the ordering workflow.

Likely future flow:

```text
User creates order
      ↓
Create unique client-side order ID
      ↓
Internet available?
   /             \
 yes              no
 ↓                 ↓
API             IndexedDB
 ↓                 ↓
Server          pending_orders
                    ↓
              connection returns
                    ↓
                  retry
                    ↓
                  API
```

The server must later use the unique client-side order ID to make order submission **idempotent**, preventing duplicate orders when unreliable connectivity causes retries.

That functionality should be added incrementally rather than as one large code dump.

# 26. Development philosophy for this project

The project is deliberately being built in phases.

Each phase should:

1. Introduce one new concept.
2. Keep responsibilities separated.
3. Prefer reusable functions/modules.
4. Explain why each new file exists.
5. Test the phase before advancing.
6. Avoid unnecessary frameworks or abstractions.
7. Preserve the developer's understanding of the complete data flow.

The goal is not merely to produce working code.

The goal is to produce working code that the developer can **understand, maintain, and extend**.
